The Spec file describes decision in much more detail. This blog entry is a high-level summary.

Monte Carlo Tree Search (MCTS) is a test-time compute strategy to find an optimal action.

In two-player games, the state is the current board, actions are possible moves (i.e. legal moves) and the goal is to find the action that maximizes the probability of winning. The moves are deterministic. One does a full MCTS search (will be described in more detail but treat it as a black-box for now) for each move since the next move is made by the opponent. MCTS generates an asymmetric tree where each node is a board state, \(s_t\) and each edge is a legal move that points the tail state (before the move) to the head state (after the move).

GPU kernel generation is a single-player game. MCTS is carried out for each workload section 5 consisting of:

  • Operation e.g. matrix multiplication

  • Hardware e.g. H100 SXM

  • dtype e.g. NVFP4

  • Tensor shape constraints e.g. each dimension in \([1024,2048]\).

The spec also includes other factors like:

  • Tensor layouts e.g. row-major contiguous matrices, column-major, strided batched tensors, interleaved QKV layouts, packed low-precision formats etc.

  • Numerical tolerances e.g. absolute (atol=\(1e-6\)) and relative (rtol=\(1e-5\)) for a given format e.g. FP32.

  • Kernel launch parameters e.g. block and grid sizes, shared memory bytes.

  • Distribution over shapes for dataset e.g. \(\mathcal{D} = {(4096,4096,4096):0.4, (8192,4096,4096):0.3, (128,4096,4096):0.2, (32,4096,4096):0.1}\). Note the reward will be an expectation over this distribution.

The list might expand over time.

Nodes

Each node (section 7) is a specific GPU kernel version for the chosen workload. The initial focus is on CUDA C++. General interfaces defining backends can be extended to CuTeDSL and CUTLASS.

Section 7 also declares a set of variables to be stored for each node. A subset is:

  • program_text: source code

  • backend_type: CUDA C++, CuTeDSL, CUTLASS

  • normalized_program_hash and binary_has_or_sass_hash: hashes of both the source code and generated SASS code. Hashes let us refer to previously computed results instead of re-evaluating performance of an already generated kernel. For more details, see section 21.

  • benchmark_results: performance results from running the node kernel version.

  • reward: numerical record of \(Q(s,a)\) i.e. average reward achieved when passing through this node.

  • lightweight_profile and full_profile: statistics from running ncu.

  • children/action statistics: priors, number of calls to each action etc.

  • created_by_strategy: record which action/strategy led to this node from its parent

  • created_by_llm_generation_id: log info about LLM session which consisted of parent node’s kernel code, strategy prompt and profile metrics which led to current node’s kernel.

Edges

An edge is a strategy/action. These prompts are stored in a config file for each backend (CUDA C++, CuTeDSL, CUTLASS).

At a given node, the action with the maximum score \(score(s,a)\) is chosen (section 9) where

\[score(s,a) = Q_{mean}(s,a) + c_{puct} P(s,a) \frac{\sqrt {\Sigma_{b} N(s,b)}}{1 + N(s,a)}\]

This strategy is known as PUCT (Polynomial Upper Confidence Trees).

Technical point: this defines the tree policy during the Expansion phase in MCTS. We don’t use rollouts here (neither does AlphaGo Zero; see section 15). At lead nodes, we profile and evaluate. AlphaGo Zero uses the value estimator at a leaf node instead of rolling out.

The first-term in the score is a direct measure of the average reward achieved when one passes through this node. In other words, all the trajectories of applying optimizations that took action \(a\) in the state \(s\) will eventually achieve some reward (log speedup) and the average value of the rewards is the first term.

The second-term encourages exploration even when the reward is low for a node. \(c_{puct}\) is a hyperparameter that weights the relative terms. \(P(s,a)\) is a prior probability assigned to each action \(a\) for a given state \(s\). This could be fixed by us (e.g. uniform prior) or generated by an LLM. \(N(s,a)\) is the number of times action \(a\) was taken in state \(s\). The term $\(\frac{\sqrt {\Sigma_{b} N(s,b)}}{1 + N(s,a)}\) effectively encourages taking an action \(a\) that has a low visitation count \(N(s,a)\) relative to the total number of visitations to the state \(\Sigma_b N(s,b)\).

Stochasticity

In a deterministic environment e.g. Go or Chess, taking an action (move) in a state (board) always results in the same final state (new board). If the same node/state is revisited, and a previously taken action is retaken, we can reuse past information.

LLMs are stochastic. At each step i.e. for each new token generation, the distribution generated by the last layer softmax is sampled which results in stochasticity.

The takeaway is that applying the same action to the same kernel source will result in different code generation for the child node.

Technical point: If the profiling is done again, there’ll also be stochasticity in ncu metrics.

Sections 10, 11, 12 describe how we treat this stochastic behavior.

Each current-node can have several children for a given strategy (unlike in determinstic settings where there is exactly one child per chosen action).

Section 11 describes a heuristic called progressive widening. This decides how many candidates to generate for a given strategy at a node. The general bound is:

\[N_{children}(s,a) \leq c_{pw} N(s,a)^{\alpha_{pw}}\]

where \(N_{children}(s,a)\) = number of children at node/state s and for action/strategy a, \(c_{pw}\) is a constant hyperparameter (default=1.0), \(N(s,a)\) is the total number of times action/strategy a was taken at node/state s and lastly, \(\alpha_{pw}\) is a hyperparameter (default=0.5).

Our default choice is:

\[N_{children}(s,a) \leq \sqrt{N(s,a)}\]

with a hard constraint that \(N_{children}(s,a)\) can never exceed a hyperparameter, \(K_{max}\) or more succinctly,

\[N_{children}(s,a) \leq \min(\sqrt{N(s,a)}, K_{max}) \]

By default, \(K_{max}=4\).

Section 12 describes exactly how progressive widening takes place. At a given node s, when an action a is taken (by using PUCT described above), we have two cases:

Case A: Allow a new child

Generate a new candidate from the LLM.

Case B: Don’t allow a new child

Support, progressive widening doesn’t allow more children. Then, we need to pick an existing child. We will simply use UCB but should explore different strategies in later iterations. UCB is described in more detail next.

Suppose, the state s with action a has 4 children:

\[s \xrightarrow{a} {s'_1, s'_2, s'_3, s'_4}\]

Since we can’t generate more children, we need a score to pick one child. UCB defines score:

\[score(s,a,s'_i) = Q(s'_i) + c_{ucb} \sqrt{\frac{\log N(s,a)}{1 + N(s,a,s'_i)}}\]

where \(Q(s'_i)\) is the average reward when one passes through \(s \xrightarrow{a} s'_i\), \(c_{ucb}\) is a scalar hyperparameter, \(N(s,a)\) is the number of times action a was called in state s, \(N(s,a,s'_i)\) is the number of times action a was called in state s and child \(s'_i\) was picked.
